# 统一评测流程 · v1.0.0

## 1. 先固定条件

推荐默认设置如下；如果调整，给所有候选使用同一设置，并写进结果记录。

| 条件 | 默认规则 |
| --- | --- |
| 起点 | 同一个基准 commit，未实现 UI 的 `starter/` |
| 框架 | 仓库锁定的 React、TypeScript、Vite 和 CSS，不增加运行时依赖 |
| 输入 | `PROMPT.md` 原文、同样三张参考图；无额外口头提示 |
| 时间 | 每次 30 分钟，自模型收到完整输入起计，包含推理和工具调用 |
| 人工反馈 | 首轮 0 次；模型在预算内自行截图、测试和修改不限次数 |
| 工具 | 为所有候选提供相同文件读写、命令、图片查看、浏览器截图能力 |
| 网络 | 评测者可预安装锁文件依赖；模型不得搜外部资产、字体或现成复刻代码 |
| 并行代理 | 默认不允许；若开放，必须对所有候选开放并另列测试条件 |
| 环境 | 相同 Node、浏览器构建、操作系统、分辨率、DPR、字体、资源限制 |
| 重复 | 每模型建议至少 3 个独立首轮运行 |

如果某个产品无法显示图片或不能操作浏览器，应记录限制，单独分组。截图可见性、工具链和模型同时变化时，结果衡量的是整套产品／agent，而不只是基础模型。

安装耗时、环境故障不混入模型预算；先确认空白工程 `npm run build` 通过，再开始。预算超时后停止生成与改动，保留当时的工作树；不要为了拿到一张好图额外修补代码。

## 2. 建立独立测试

```bash
git rev-parse HEAD
git switch -c run/model-a-01
cd starter
npm ci
npm run build
```

把基准 commit 记入 `results/template.json`。每次重复使用全新上下文和同一个空白工程，不复用前一个模型的实现、修复指令或缓存状态。分支命名可以匿名化，不需要把真实模型名称放在截图上。

如果模型只能接收附件：附上三张原图，不能只把 README 中的缩略图截图发过去。不要替某个模型裁成更易理解的版本；其自行裁切属于本轮能力和耗时。

## 3. 把输入发给模型

原文发送 `PROMPT.md`。告诉模型工程目录是 `starter/`，其余规则均在 Prompt 内。

不补充设计倾向，不对某个模型额外解释“为什么不像”，不引导其换浅色主题。使用完全相同的输入语言和版本。如果做英文或浅色扩展题，建立新版本或新轨道，成绩不要混在 v1.0.0 中。

## 4. 模型完成后收集证据

在候选工程里执行 `npm run build`，并启动：

```bash
cd starter
npm run dev -- --host 127.0.0.1
```

根目录安装评测依赖并收集证据：

```bash
npm ci
npx playwright install chromium
npm run capture -- --url http://127.0.0.1:5173 --out runs/model-a-01/evidence
```

保留 `capture.json` 和全部 PNG，包括检查失败时产生的初始截图。`capture.json` 区分断言失败与脚本错误，并记录浏览器版本、控制台错误和网络请求失败。脚本退出码 1 不代表候选视觉分必定为 0，需要查看失败原因。

脚本覆盖以下顺序，每次截图关闭 CSS 动画并等待字体与图像加载，不改变实际应用状态：

| 阶段 | 操作／证据 |
| --- | --- |
| desktop-initial | 全新上下文，桌面初始画面，Mario 选中，完整机身＋双屏局部 |
| desktop-eshop | 点击 eShop，选中框及上屏名称更新 |
| desktop-open | 点击 Open，打开 eShop 占位页 |
| desktop-return | 点击 Back，保留 eShop 选择 |
| hardware-controls | A 打开、B 返回、A 再打开、HOME 返回、十字键向右／左移动 |
| keyboard | 切回 Mario，方向键向右／左，Enter 打开，Escape 返回 |
| desktop-settings | 点击设置，名称变成 System Settings |
| mobile-initial | 另一个全新上下文，移动端初始画面及触控打开／返回检查 |

按键连发、边缘不循环、其余 25 个图标是否各自更新预览，另做人工检查。自动脚本覆盖一部分基础功能，不是完整系统测试。

## 5. 视觉评分

- 对照图 1 的上屏／下屏和图 2 的机身分别打分，使用 [RUBRIC.md](RUBRIC.md)。
- 固定截图尺寸；不要只展示最漂亮的一块局部，不要手工缩放每个候选以掩盖比例差异。
- 软件原图裁切位置见 `benchmark.json`，可以把候选双屏截图等比缩放到相应逻辑画布对照。像素级差异只作辅助，不作为唯一总分：参考图低分辨率、机身照片透视和字体渲染都会影响它。
- **没有“机身＋深色 UI”的官方合成目标图。** 不存在可靠的整页像素金标准；不要把硬件图中的浅色屏幕当成整页目标。
- 第三张浅色图不单独评分；不能因为模型没做宝可梦或主题切换而扣分。
- 最好由 2 名不知道模型身份的评测者独立打分；逐项分歧超过 20% 时复核，保留理由。只用一名评测者也要注明。

## 6. 记录与比较

复制 `results/template.json` 成本次结果，填写实际模型标识、推理设置、agent 产品、工具、时间和可获得的 token 使用量；拿不到的字段保持 `null`。

填写各项得分、扣分理由和证据相对路径，再执行：

```bash
npm run verify-run -- results/model-a-01.json
```

该命令仅验证记录的结构、得分范围、总分和必填信息，不替你打分。不要把尚未完成的 template 当成成绩。

分别报告视觉分 `/80`、交互分 `/15`、工程分 `/5` 和总分 `/100`。重复运行报告中位数、最低和最高，不只挑最佳结果。人工追加修复轮应另表记录，不能覆盖首轮结果。

`runs/` 默认被忽略。公开结果前删除访问令牌、账号、私人对话和内部公司内容；只提交获准公开的摘要和证据。失败运行也保留，不把失败当作基础设施问题静默排除。
